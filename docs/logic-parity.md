# Ham logic parity

This document is the single place to check **whether iOS and Android implement the same business
rule**. It is derived from a read-only, cross-platform audit of the business-logic code in
`ham-ios` and `ham-android` (parsing, calculation, storage, gating, networking, scheduling) — not
from the UI.

It is **not** the place for colours, padding, typography or string wording. Those live in
`design-system.md`, `screens.md` and `copy-and-strings.md`. Where this document says "the two
clients disagree about whether a course is current", that is logic; where they paint it a
different colour, that is `design-system.md`.

**How to use it.** Before changing behaviour on one platform, find the rule here. If there is a
row, the Verdict column tells you whether the other platform already does it your way, and the
Action column says which side moves. If there is no row, check §11 (Agreed behaviour) — if it is
not there either, you are inventing new behaviour and should add a row.

`file:line` citations are preserved from the audit so you can jump straight to the code. Where a
behaviour is absent on a platform, the audit records **not found** — that is a deliberate claim
(searched and absent), not an omission.

## 1. How to read this

Every entry has the same five parts:

| Part | Meaning |
|---|---|
| **Rule** | The agreed behaviour, stated prescriptively. What *should* happen. |
| **iOS** | What `ham-ios` currently does, with `file:line`. |
| **Android** | What `ham-android` currently does, with `file:line`. |
| **Verdict** | 🔴 / 🟠 / 🟡 plus which side is right, or `both wrong`. |
| **Action** | The concrete change. One platform is named unless both must move. |

**Severity**

| | Meaning |
|---|---|
| 🔴 | **User-visible divergence.** The same user action produces a materially different result on the two platforms — a different number, a different day, a crash, a missing feature. |
| 🟠 | **Robustness or correctness divergence.** Same behaviour on the happy path; different failure mode, crash risk, or silent data loss when something goes wrong. |
| 🟡 | **Internal divergence.** No direct user impact today, but the code paths differ and will diverge visibly as soon as either side is extended. |

**Conventions**

- **not found** — the behaviour does not exist on that platform. Searched and absent.
- Where a widely-believed premise about a divergence was checked during the audit and **refuted**,
  the refutation is recorded at the end of the relevant section. Do not re-open it without new
  evidence.
- Items that exist on only one platform at all are in §10, not in the per-section tables.
- Rules the two platforms already agree on are in §11 and are **not** re-litigated here.

## 2. Timetable and courses

The timetable is the most-used surface in the app and the most diverged. Three of the top five
items here change what a user sees on every single launch.

### 2.1 Colour assignment

| Rule | iOS | Android | Verdict | Action |

### 8.1 The "iOS passes the CAS session id as the PIN" claim — REFUTED

**There is no `pin` identifier, parameter, or protobuf field in either codebase. There is no such
call on iOS and no counterpart on Android. There is no PIN divergence to fix.**

Verified four independent ways: repo-wide `\bpin\b` over `ham-ios/Ham` (`.swift`, `.proto`) matches
only vendored SwiftUIX SF-Symbol tables and Realm pod internals — zero app-code hits; `\bpin\b|
passcode|pin_code` over `ham-android` returns 0 results; `\bpin\b` over `.cache/ham-proto/`
(16 files) returns 0, and `login.proto:17-23` defines `LoginRequest` with exactly five fields
(`login_type`, `data`, `device_id`, `device_desc`, `extend_info`) and no PIN slot; the library sync
request bodies have three fields and no PIN (`HamSyncLibraryPostTokenRequest.swift:13-16`,
`.kt:17-21`).

What the report was most likely describing — two real things, **neither is a PIN**:

1. **`studentIDSecret`** — the only CAS-derived value on the account-login path, and it is a
   **student ID, not a session id** (`HamAccountManager.swift:88-90`, `AccountManager.kt:63`). The
   CAS *cookie* is read only in `CasRequestHelper.swift:15-20` / `.kt:21` and never on any account
   or sync login path on either platform.
2. **The synced library token's `userId`** — `LibrarySyncService.swift:65,82,127` send
   `storage.getStringValue(.library_userId).md5.uppercased()`; a hashed school/library user id on
   the **library-token sync** call, not on sign-in.

Also ruled out: Android's only `/auth/signIn` endpoint is `LibraryPCApi.kt:116`, the library
seat-booking login — unrelated to account sync.
